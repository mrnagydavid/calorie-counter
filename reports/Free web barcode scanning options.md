# Fix your own scan pipeline first

Most wrong values come from the app's own accept rule, not from the decoder. Today the scanner takes the first frame that gives 8, 12, 13 or 14 digits. It does not check the GS1 check digit. It also reads ITF and Code 128, and it does not wait for a second frame that agrees. **Fix these three items first.** They are free, they need no new library, and serious scanner engines all do them ([Dynamsoft](https://www.dynamsoft.com/barcode-reader/docs/core/performance/accuracy.html), [STRICH](https://docs.strich.io/reference/interfaces/EngineConfiguration.html)). Poor focus comes mostly from the lens that the browser opens. **Open the back camera by `deviceId`**: on an iPhone Pro, the virtual "Back Triple Camera" or "Back Dual Wide Camera"; on Android, the back camera that reports continuous autofocus. Keep the native `BarcodeDetector` on Android. On iOS, replace html5-qrcode (last release April 2023) with `zxing-wasm` in your own camera code. Build a native Capacitor app only if these steps fail, because iOS then needs a re-install every 7 days or $99 each year. **Do not buy a scanner SDK.** No vendor sells a one-time licence for browser scanning, the cheapest plan costs €99 each month, and no web SDK gets more focus control from Safari than your own code gets.

## Eleven changes, ranked by impact against effort

| # | Change | Fixes | Effort | Where in the code |
|---|---|---|---|---|
| 1 | Remove `code_128` and `itf` | Wrong values | Very small | `SCAN_FORMATS` in `barcodeDetector.ts`; `FORMATS` in `Html5QrcodeScanner.tsx` |
| 2 | Check the GS1 check digit; expand UPC-E to UPC-A first | Wrong values | Small | `isValidBarcode` in `barcodeDetector.ts` |
| 3 | Accept a code only when 2 of the last 5 frames agree (3 on html5-qrcode) | Wrong values from blur | Small | the `hit` branch in `detectLoop`; the success callback in `Html5QrcodeScanner.tsx` |
| 4 | Convert every code to one form before lookup and storage | Saved foods and cache rows that do not match | Small, plus a one-time data change | `handleBarcode` in `BarcodeScanner.tsx`; `barcode` keys in `customFoods` and `barcodeCache` |
| 5 | iOS: open the virtual back camera by `deviceId` | Blur on iPhone Pro models | Small to medium | `scanner.start({ facingMode: 'environment' }, …)` |
| 6 | Android: open the back camera with continuous autofocus; add tap-to-focus | Blur where Chrome picks a wrong lens | Medium | `getUserMedia` in `startCamera` |
| 7 | Decode a wide centre strip, not the full frame; widen the iOS scan box | Wrong values, speed | Small to medium | `detector.detect(video)`; `qrbox: { width: 250, height: 150 }` |
| 8 | iOS: replace html5-qrcode with `zxing-wasm` in your own camera code | Wrong values, camera control, dead dependency | Medium | `Html5QrcodeScanner.tsx`; reuse the camera code of `NativeBarcodeScanner.tsx` |
| 9 | Add a "Take a photo" fallback | Codes that live scan cannot focus on | Medium | new button on the scan screen |
| 10 | Wrap the PWA in Capacitor with a native scanner | Both problems | Large, plus iOS signing cost | new native projects |
| 11 | Buy a web scanner SDK | Read rate on damaged codes | No one-time option exists | — |

Do rows 1–4 as one change. They add no dependency and they help both phones. Then do rows 5–7 for focus. Do row 8 only if iOS still fails after that. Rows 10 and 11 are not recommended for this app. Before you start, log the `format`, the raw value, the check-digit result and the scanner path for each read. The log shows which phone and which format give the wrong values.

## Three missing checks let wrong digits through

The decoders do part of the work. ZXing-js, zxing-cpp, ZBar and Quagga2 all reject an EAN-13, EAN-8 or UPC-A read with a bad check digit ([zxing-js](https://github.com/zxing-js/library/blob/master/src/core/oned/UPCEANReader.ts), [zxing-cpp](https://github.com/zxing-cpp/zxing-cpp/blob/master/core/src/oned/ODMultiUPCEANReader.cpp)). On Android, Chrome sends the frame to the Play Services Mobile Vision API and adds no check of its own ([Chromium](https://chromium.googlesource.com/chromium/src/+/main/services/shape_detection/android/java/src/org/chromium/shape_detection/BarcodeDetectionImpl.java)). Google does not document what Mobile Vision checks. The check digit also has limits. It finds **every single-digit error and 90% of swapped neighbour digits** ([Wikipedia](https://en.wikipedia.org/wiki/International_Article_Number)). But about **1 in 10 reads with two or more wrong digits still pass**. For example, 4006381333931 and 4105381333931 both have a valid check digit. html5-qrcode users report this pattern: "the SAME barcode gives me back 10 different decodeText" ([html5-qrcode #744](https://github.com/mebjas/html5-qrcode/issues/744)). A 2026 ZXing-js report says "often the first 4–5 digits wrong" ([ngx-scanner #601](https://github.com/zxing-js/ngx-scanner/issues/601)).

On iOS, the check is weaker. The ZXing-js copy inside html5-qrcode 2.3.8 checks a UPC-E code over its 8 short digits. GS1 requires the check over the expanded 12-digit UPC-A ([zxing-js UPCEReader.ts](https://github.com/zxing-js/library/blob/master/src/core/oned/UPCEReader.ts), [html5-qrcode bundle](https://unpkg.com/html5-qrcode@2.3.8/third_party/zxing-js.umd.js)). As a result, **the real UPC-E code 04252614 fails, and a wrong UPC-E passes about 1 time in 10**. This finding comes from the source code. Nobody has confirmed it on a device.

**Remove ITF and Code 128.** GS1 uses ITF-14 and GS1-128 on cases and pallets, not on retail packs ([GS1](https://www.gs1.org/docs/barcodes/GS1%2520Barcodes%2520Fact%2520Sheet%2520-%2520GS1%25201D%2520symbols%2520for%2520general%2520distribution%2520only.pdf)). ITF has no required check digit. ZXing accepts ITF values of 6, 8, 10, 12, 14 or more digits ([zxing-js ITFReader.ts](https://github.com/zxing-js/library/blob/master/src/core/oned/ITFReader.ts)). So an ITF misread of 8, 12 or 14 digits passes `isValidBarcode` with no check at all. Code 128 is safer, but a GS1-128 value starts with an application identifier and is too long for your length filter. Both formats add risk and decode time, and neither helps a food app. Dynamsoft states that a shorter format list lowers misreads ([Dynamsoft](https://www.dynamsoft.com/barcode-reader/docs/core/performance/accuracy.html)).

**Wait for agreement.** zxing-cpp accepts a 1D code only when **2 scan lines in the frame agree** (`minLineCount`) ([zxing-cpp](https://github.com/zxing-cpp/zxing-cpp/blob/master/core/src/ReaderOptions.h)). STRICH needs 2 sightings over time for 1D codes with weak checksums ([STRICH](https://docs.strich.io/reference/interfaces/EngineConfiguration.html)). Dynamsoft needs **the same result twice in 5 frames** ([Dynamsoft](https://www.dynamsoft.com/barcode-reader/docs/core/performance/accuracy.html)). Quagga users accept 3 equal results in a row ([quaggaJS #237](https://github.com/serratus/quaggaJS/issues/237)). Your loop runs about 9 times each second (`DETECT_INTERVAL_MS = 110`), so "2 of the last 5 frames" adds only 100–500 ms. Use 3 on the html5-qrcode path, because ZXing-js accepts the first single row that decodes ([zxing-js OneDReader.ts](https://github.com/zxing-js/library/blob/master/src/core/oned/OneDReader.ts)). The vote also fixes a timing problem. With continuous autofocus, the first frames are often blurred, and "first frame wins" takes exactly those frames. Count votes only for codes that pass row 2, after the conversion in row 4.

**Convert each code to one form.** ML Kit and ZXing-js return a 13-digit code that starts with 0 as a 12-digit UPC-A ([ML Kit #797](https://github.com/googlesamples/mlkit/issues/797), [zxing-js](https://github.com/zxing-js/library/blob/master/src/core/oned/MultiFormatUPCEANReader.ts)). zxing-cpp now returns the same code as 13 digits ([barcode-detector #184](https://github.com/Sec-ant/barcode-detector/issues/184)). Open Food Facts adds the 0 itself, so its lookup works for both forms ([Open Food Facts](https://openfoodfacts.github.io/openfoodfacts-server/api/ref-barcode-normalization/)). Your own tables do not. `lookupBarcode` and the saved-food check use the raw string as the key. A food saved under 034000470693 does not match a later scan of 0034000470693. Use this rule: UPC-A gets a leading 0; UPC-E expands to UPC-A and then gets a leading 0; a 14-digit code that starts with 0 loses that 0; EAN-8 stays 8 digits. Convert the stored `barcode` values once, with the existing `dataVersion` field. Do this before any decoder change, because a new decoder can change the form.

What you will see: today, a blurred frame can read 4105381333931, and the screen shows "No product found for this barcode". After rows 1–4, the camera stays open until two frames read 4006381333931, and then the product shows. One side note: the manual-entry placeholder "e.g. 7622210100234" has an invalid check digit. If you also put the check on the "Look up" button, change the placeholder.

## The browser picks the lens, and on iPhone Pro it picks badly

The focus problem is mostly a lens problem. On **iPhone 13 Pro and newer Pro models, the main back lens cannot focus closer than about 15–20 cm** ([WebKit bug 247737](https://bugs.webkit.org/show_bug.cgi?id=247737), [Apple forums](https://developer.apple.com/forums/thread/721603)). Older non-Pro iPhones focus at about 4 cm. Scanbot reports the same problem on iPhone 14, 15 and 15 Plus ([Scanbot](https://docs.scanbot.io/faq/common_web_integration_issues/)). A grocery barcode at 10 cm is therefore blurred on that lens, at any resolution.

Safari can solve this. Since iOS 16.3, `enumerateDevices()` lists every back lens and Apple's virtual devices, "Back Triple Camera" and "Back Dual Wide Camera" ([Schilling](https://dominikschilling.de/notes/ios-access-all-back-cameras-mediadevices-api/), [WebKit bug 250142](https://bugs.webkit.org/show_bug.cgi?id=250142)). **A virtual device switches to the ultra-wide macro lens at close range by itself.** WebKit maps web zoom 1 to device zoom 2 on these devices, so the preview looks normal ([WebKit commit](https://github.com/WebKit/WebKit/commit/1ed9893d37)). The commercial SDK STRICH opens "Back Dual Wide Camera" by default since February 2024, because "Back Camera" "resulted in bad scanning performance due to the camera being out of focus" ([STRICH changelog](https://docs.strich.io/CHANGELOG.md)). No primary source says which device `facingMode: 'environment'` opens on iOS 17–26. One library maintainer says it is the virtual camera since iOS 16.4 ([quagga2 #396](https://github.com/ericblade/quagga2/issues/396)). Select the device yourself to remove the guess.

Do it like this. Call `getUserMedia` once, so the labels fill in. Call `enumerateDevices()`. Pick "Back Triple Camera", then "Back Dual Wide Camera", then "Back Camera". Open it with `deviceId: { exact: id }`. The labels change with the phone language: STRICH opened the wrong camera in French until December 2025 ([STRICH changelog](https://docs.strich.io/CHANGELOG.md)). As a language-free test, a virtual device reports `zoom.min` 0.5 in `getCapabilities()` ([WebKit source](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/platform/mediastream/cocoa/AVVideoCaptureSource.mm)). This test comes from the source code and is not tried on a device. html5-qrcode can take a camera id in place of `{ facingMode }`, but this research did not confirm it.

Safari gives the page little else. It has **no `focusMode`, no `pointsOfInterest` (tap-to-focus) and no exposure control** ([WebKit source](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/platform/mediastream/cocoa/AVVideoCaptureSource.mm)). It does support `zoom` since Safari 17 ([WebKit](https://webkit.org/blog/14445/webkit-features-in-safari-17-0/)) and `torch` since about iOS 17.4 ([WebKit bug 243075](https://bugs.webkit.org/show_bug.cgi?id=243075)). If only the plain "Back Camera" exists, apply `zoom: 2` and tell the user to hold the phone 20–25 cm away. html5-qrcode limits you further: users report a blurrier, lower-resolution stream from it ([html5-qrcode #820](https://github.com/mebjas/html5-qrcode/issues/820)).

Android has the opposite problem: Chrome shows every lens. Chrome lists each camera that Android reports as a separate `videoinput`, and it does not filter ultra-wide or fixed-focus lenses ([Chromium](https://github.com/chromium/chromium/blob/main/media/capture/video/android/java/src/org/chromium/media/VideoCaptureCamera2.java)). Several apps found that `facingMode: 'environment'` opened a lens that cannot focus close ([kept #486](https://github.com/keptinventory/kept/issues/486), [Cellarion #1483](https://github.com/jagduvi1/Cellarion/pull/1483)). Their fix: list the back cameras, keep the one whose `getCapabilities().focusMode` contains `'continuous'`, and prefer the lowest "camera2 N, facing back" ([bindarr #100](https://github.com/thenotoriousJeremy/bindarr/pull/100)). Save the `deviceId`. Chrome also supports **tap-to-focus**: send `{ pointsOfInterest: [{ x, y }], focusMode: 'single-shot' }`, then go back to `'continuous'`. Chrome uses the same point for exposure, which helps on glossy packs ([Chromium](https://github.com/chromium/chromium/blob/main/media/capture/video/android/java/src/org/chromium/media/VideoCaptureCamera2.java)). Some Samsung phones ignore focus and zoom in web apps, and no fix is known ([Samsung forum](https://forum.developer.samsung.com/t/camera-auto-focus-and-zoom-camera-not-working-in-the-web-application/27908)).

Resolution does not fix focus. Vendors use 720p by default ([STRICH](https://docs.strich.io/reference/interfaces/FrameSourceConfiguration.html)). ML Kit asks for at least 2 px per bar module, which is **190 px across an EAN-13** ([ML Kit](https://developers.google.com/ml-kit/vision/barcode-scanning/android)). Your 1920×1080 request is enough. A 250 px iOS scan box is too narrow for a code that the user holds far away, so widen it to about 80% of the view. For codes that live scan still cannot read, add a "Take a photo" button. `<input type="file" accept="image/*" capture="environment">` opens the phone's own camera, which uses the macro lens ([MDN](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/capture), [WebKit bug 253186](https://bugs.webkit.org/show_bug.cgi?id=253186)). It costs more taps and needs a decoder for still images.

## Swap the iOS decoder, keep Android native

html5-qrcode will not get better. Its last npm release is **2.3.8 from 15 April 2023**. Its README says the project is "in maintenance mode" and pull requests "won't be merged" ([html5-qrcode](https://github.com/mebjas/html5-qrcode#readme)). It ships an old ZXing-js copy that accepts the first single row that decodes, and it turns `TRY_HARDER` off ([html5-qrcode decoder](https://github.com/mebjas/html5-qrcode/blob/master/src/zxing-html5-qrcode-decoder.ts)). Open issues report wrong EAN-13 values ([#407](https://github.com/mebjas/html5-qrcode/issues/407), [#744](https://github.com/mebjas/html5-qrcode/issues/744)). It also owns the camera, so rows 5 and 7 are hard to do with it.

**Use `zxing-wasm` directly on iOS.** It wraps ZXing-C++, has an MIT licence, and had a release on 15 November 2026 ([npm](https://www.npmjs.com/package/zxing-wasm)). Call `readBarcodes()` on an `ImageData` from your own camera loop ([zxing-wasm](https://github.com/Sec-ant/zxing-wasm#readme)). Set `formats` to EAN-13, EAN-8, UPC-A and UPC-E. Set `minLineCount` to 3 and `maxNumberOfSymbols` to 1 ([ReaderOptions](https://sec-ant.github.io/zxing-wasm/docs/interfaces/full.ReaderOptions.html)). The `barcode-detector` ponyfill that you tried passes only `formats`, so you cannot raise `minLineCount` through it ([barcode-detector source](https://unpkg.com/browse/barcode-detector@3.2.4/dist/es/zxing-exported.js)). The reader WASM is **410 KB gzip or 323 KB Brotli** ([unpkg](https://unpkg.com/browse/zxing-wasm@3.1.7/dist/reader/)). By default it loads from jsDelivr. Set `locateFile` to a self-hosted copy, and let Workbox precache it ([zxing-wasm](https://github.com/Sec-ant/zxing-wasm#readme)). Reuse the camera code of `NativeBarcodeScanner.tsx`. Then iOS also gets the lens choice, zoom, torch and crop from rows 5 and 7.

The evidence favours ZXing-C++ for correctness, not for read rate. In a vendor benchmark, it gave **1 wrong EAN-13 in 793 results** on the Muenster set and 26 in 1,290 on DEAL Lab ([Dynamsoft 1D benchmark](https://dynamsoft.com/codepool/barcode-scanning-accuracy-benchmark-and-comparison.html)). Its read rate was lower: 75% on Muenster, against 97% for Dynamsoft. In a browser test, zxing-wasm read **78.5% of EAN-13 codes, against 97.3% for Dynamsoft** ([Dynamsoft JS benchmark](https://www.dynamsoft.com/codepool/benchmark-barcode-reading-javascript-zxing-wasm-dynamsoft-barcode-reader.html)). Dynamsoft sells the competing SDK, so treat these numbers with care. No benchmark compares html5-qrcode and zxing-wasm on live video.

Your earlier trial does not contradict this plan. That trial put ZXing-C++ against native ML Kit, and this plan keeps ML Kit on Android. On iOS, the comparison is against html5-qrcode instead. The trial also used the same `facingMode` camera setup, so it did not test the lens fix. And it returned UPC-A codes as 13 digits, which looks like a different value without row 4 ([barcode-detector #184](https://github.com/Sec-ant/barcode-detector/issues/184)). Do not use Quagga2: its README says it "may produce false positives" ([quagga2](https://github.com/ericblade/quagga2#readme)). Do not use ZBar-WASM. ZBar gave **34 wrong reads on Muenster and 8 on blurred images, against 1 and 2 for ZXing-C++** ([Dynamsoft 1D benchmark](https://dynamsoft.com/codepool/barcode-scanning-accuracy-benchmark-and-comparison.html)), and its WASM package has had no release since May 2024 ([npm](https://www.npmjs.com/package/@undecaf/zbar-wasm)).

## A native app fixes the camera but adds weekly chores

Capacitor gives the best camera at the highest cost. On Android, `@capacitor-mlkit/barcode-scanning` has a `scan()` call that opens the Google Code Scanner screen and needs **no camera permission** ([Capawesome](https://github.com/capawesome-team/capacitor-mlkit/tree/main/packages/barcode-scanning)). On iOS, the free `@capacitor/barcode-scanner` uses Apple Vision ([Capacitor](https://capacitorjs.com/docs/apis/barcode-scanner)). The Capawesome plugin uses ML Kit on iOS, and its Apple Vision version is a paid sponsor product. Your Preact code, router and Dexie stay. Only the scan call changes, behind `Capacitor.isNativePlatform()`.

The real costs are outside the code. **A free Apple account signs an app for 7 days only**, so you must rebuild and reinstall each week ([Apple](https://developer.apple.com/support/compare-memberships/)). SideStore can do the refresh for you ([SideStore](https://docs.sidestore.io/docs/faq)). A one-year install needs the **Apple Developer Program at $99 each year**, which is a periodic fee. iOS builds need a Mac with Xcode. The native app is a new origin, so its IndexedDB starts empty and you must move your data once. iOS can also delete WebView storage when the phone is low on space ([Capacitor](https://capacitorjs.com/docs/guides/storage)). Android is free: install the APK with ADB. Google's developer verification goes global in 2027, but ADB installs stay open ([Google](https://support.google.com/android-developer-console/answer/16561738?hl=en)).

No independent test shows that ML Kit or Apple Vision misread EAN-13 less often than ZXing-C++. The vendor data uses still images with many codes and gives no misread counts ([Dynamsoft iOS benchmark](https://www.dynamsoft.com/codepool/ios-barcode-scanner-benchmark-app-swiftui.html)). The native gain is the camera pipeline: autofocus, lens switching and auto-zoom. Two no-code routes exist, and both have a catch. On Android, the free Binary Eye app opens a return URL with the code, `binaryeye://scan?ret=…{RESULT}` ([Binary Eye](https://github.com/markusfisch/BinaryEye)). Nobody has tested the return into an installed PWA. On iOS, a Shortcut with "Scan QR/Barcode" can open your URL with the code ([Apple](https://support.apple.com/guide/shortcuts/use-x-callback-url-apdcd7f20a6f/ios)). But iOS opens that URL in Safari, and **a home-screen web app does not share storage with Safari** ([firt.dev](https://firt.dev/notes/pwa-ios/)). So the scan lands in an empty copy of your app.

A paid SDK also cannot fix iPhone focus. Paid web SDKs use the same `getUserMedia` stream as your code, and Safari gives no focus control to any page. Apple's own fix, a zoom based on `minimumFocusDistance`, exists only in native code ([Apple forums](https://developer.apple.com/forums/thread/715568)). The vendors' iPhone fix is the lens choice in row 5 ([STRICH changelog](https://docs.strich.io/CHANGELOG.md), [Scanbot](https://docs.scanbot.io/faq/common_web_integration_issues/)), which you can copy for free. Their real lead is read rate on damaged or blurred codes, not correctness on a clean pack held still. STRICH Basic also breaks your offline-first rule: a scan in a shop with no signal can fail. If you want a reference point, use a **free 30-day trial of Dynamsoft or barKoder, with no credit card** ([Dynamsoft](https://www.dynamsoft.com/barcode-reader/pricing/), [barKoder](https://barkoder.com/pricing)). Compare it with the fixed free pipeline on your own groceries. Do not pay.

## Conclusion

Your two complaints are one problem. Blur produces wrong digits. On out-of-focus EAN-13 images, ZXing-C++ read only 22 of 215 codes, and 2 of its 24 results were wrong ([Dynamsoft 1D benchmark](https://dynamsoft.com/codepool/barcode-scanning-accuracy-benchmark-and-comparison.html)). So the lens fix lowers wrong values, and the vote makes the remaining blur errors harmless. After rows 1–4, a wrong value must pass the check digit by chance and then repeat in a second frame. Random errors rarely do both. The remaining failure is then "no read", not "wrong product".

That changes the spending question. Paid SDKs and native scanners win on read rate, not on correctness. So decide on them only with data from your own phone. Keep the log for a week after rows 1–7. If iOS still misses codes, do row 8. If a phone still misses codes after that, build the native Android app first, because it costs nothing. No step in this plan needs money. The only paid item that helps, the Apple Developer Program, is a yearly fee, and free 7-day signing does the same job with more effort.
